# 角色与权限设计

WINS Internal Admin 使用固定岗位角色，而不是允许管理员随意勾选单项权限。这样可以确保前端菜单、页面操作、Server Action 与 Supabase RLS 使用同一套权限边界。

## 角色定位

| 角色 | 主要职责 | 典型权限边界 |
| --- | --- | --- |
| 系统管理员 | 账号、角色、系统配置与最终授权 | 拥有完整权限，建议仅分配给少数负责人 |
| 运营负责人 | 订单、客户、报价、资源与业务统筹 | 可修改大部分运营数据，不能管理账号与系统设置 |
| 销售与客户 | 客户关系、询价、报价与转化 | 可维护客户和报价，订单只读 |
| 财务与对账 | 回款、供应商付款、成本与利润 | 可维护财务数据，业务订单只读 |
| 调度执行 | 排车、司机、导游和订单执行 | 可维护执行资源与订单，不能查看财务与系统设置 |

## 分配规则

- 新注册账号由 Supabase trigger 自动建立为 `operations`，管理员应在账号启用前确认其正式岗位角色。
- 角色变更会立即影响左侧导航、页面访问、按钮操作和数据库写入策略。
- 管理员不能直接修改自己的角色或停用自己的账号。
- 系统会阻止停用或降级最后一个启用中的管理员；该规则同时存在于后台操作和 PostgreSQL trigger 中。
- 离职或暂时不需要访问后台的成员应设为停用，而不是删除档案。

## 安全边界

- 普通用户不能直接插入或更新自己的 `profiles` 记录，避免自行提升为管理员。
- 账号角色与状态只能由管理员通过系统设置页维护。
- 停用账号的 `current_app_role()` 会返回空角色，即使旧登录令牌仍未过期，也无法继续通过 RLS 读取或写入业务数据。
- 主要业务表读取会按岗位角色限制；客户和订单基础信息作为调度执行所需的共享业务参考，对全部正式岗位角色开放。
- Dashboard 会隐藏当前角色不能访问的模块入口和敏感利润区域。
- 关键角色调整和账号启停会写入 `audit_logs`。
- 当前订单金额字段仍与订单执行资料存放在同一张 `orders` 表中。如果未来需要做到数据库字段级别的商业金额隔离，应把订单财务字段拆分到独立财务表，并为该表单独设置 RLS。
- 修改角色设计时，需要同步检查：
  - `lib/auth/roles.ts`
  - 页面与 Server Action 的 `hasPermission(...)`
  - `supabase/schema.sql` 中的 RLS 策略

## 上线升级

角色安全策略升级后，需要在 Supabase SQL Editor 执行最新版 `supabase/schema.sql`。执行后，旧的 `users_insert_own_profile` 和 `users_update_own_profile` 策略会被移除，新用户档案继续由 `auth.users -> profiles` trigger 自动创建。
